# v0.6.0 — Provider add must not delete itself

Status: planned for 0.6.0. No migration.

## Symptom

Adding a provider can make the row disappear immediately. The dialog may close or
show only a generic message, so the user cannot tell whether the key, the base
URL, the network or the app failed.

## Root cause

The add flow treats verification as part of the save transaction:

- `src/components/settings/ProvidersPage.tsx` (`ProviderDialog.save`) calls
  `saveConnection`, then `setApiKey`, then `verifyProvider`.
- `src/lib/store.tsx` (`saveConnection`) inserts the row, sets it active and
  refreshes the list before verification.
- On any error after the insert, `ProvidersPage` calls
  `rollbackConnection(removeConnection, savedId)`, and `removeConnection`
  deletes the row and its key.

That means a transient network error, a 401/403, a 404 from `/models`, an empty
model list or a provider that does not implement `/models` all delete the new
provider. Verification is being used as a save gate rather than a diagnostic.

The message is often not definite because `src/lib/utils.ts` (`errorText`) only
unwraps `Error` and `string`. Tauri serializes `AppError` as an object such as
`{ "Upstream": "HTTP 401 …" }`; `src/lib/api.ts` already has
`formatInvokeError` for that shape, but `ProvidersPage` uses `errorText`. The
dialog therefore falls back to “Something went wrong. Please try again.” or the
generic provider hint.

`rollbackConnection` also swallows its own failure with `console.warn`, so a
failed delete can leave a row behind with no explanation.

## Ollama Cloud: current setup is not allowed by the docs

Ollama's official docs allow the base URL and key shape the app uses:

- `https://docs.ollama.com/api/authentication`: direct cloud inference at
  `https://ollama.com/api` and `https://ollama.com/v1` requires an API key in
  `Authorization: Bearer`.
- `https://docs.ollama.com/api/openai-compatibility`: the OpenAI client uses
  `base_url="https://ollama.com/v1"` with `OLLAMA_API_KEY`.
- `https://docs.ollama.com/cloud`: list cloud models with
  `https://ollama.com/api/tags`.

The app's extra key probe is not documented:

```rust
// src-tauri/src/llm.rs, verify_provider
client.get("https://ollama.com/api/me").bearer_auth(&key).send()
```

`/api/me` is absent from `https://docs.ollama.com/llms.txt` and
`https://docs.ollama.com/openapi.yaml`. A plain `GET https://ollama.com/api/me`
returns `405 Method Not Allowed` even without a key, so a valid Ollama Cloud key
is reported as rejected and the new provider is rolled back.

The model-list endpoints do not prove the key either: both
`https://ollama.com/v1/models` and `https://ollama.com/api/tags` return `200`
without an API key. The documented endpoint that does validate the key is
`GET https://ollama.com/api/balance` with the bearer token; it returns `401`
without a key.

## Fix

1. **Separate save from verification.**
   - Persist the row and key first.
   - Run `verifyProvider` as a non-destructive check.
   - On failure, keep the row and the dialog open. Show the provider name, base
     URL, step (`saving key`, `checking models`), HTTP status and raw provider
     message.
   - Offer `Retry test`, `Keep provider` (save without a successful test) and
     `Delete`.
2. **Rollback only persistence failures.**
   - Delete the row only when the insert or key write itself failed.
   - Never delete because `/models` returned an error or an empty list.
3. **Do not activate before verification.**
   - Keep the previous active connection until the new provider is saved
     successfully, so a failed test cannot trigger a second model refresh and a
     second error.
4. **Use the existing error formatter.**
   - Make `errorText` delegate to `formatInvokeError`, or use
     `formatInvokeError` in every provider path.
   - Keep `classifyStreamError` for the human hint, but always append the raw
     message.
5. **Report rollback failure.**
   - Replace the silent `console.warn` with a toast or inline error that names
     the provider and says the row could not be removed.
6. **Show a persistent result.**
   - Keep the last test result on the provider card after the dialog closes, so
     the user can read it without reopening the dialog.
7. **Fix Ollama Cloud verification.**
   - Delete the `GET https://ollama.com/api/me` probe.
   - For `ollama-cloud`, validate with the documented
     `GET https://ollama.com/api/balance` bearer request, or skip the key probe
     and let the first chat request report the auth error.
   - List models with `https://ollama.com/v1/models`, then fall back to
     `https://ollama.com/api/tags`; do not treat either public list as proof that
     the key is valid.

## Tests

- `verifyProvider` rejects with `{ Upstream: "HTTP 401 …" }`: row remains, dialog
  stays open, exact message is visible.
- Ollama Cloud: `/api/me` is never called; `/api/balance` returns `200` for a
  valid key and `401` for a bad key; `/v1/models` falls back to `/api/tags`.
- `/models` returns `404`: row remains and can be kept for chat-only providers.
- Network timeout: row remains with a network hint.
- Database insert fails: no row, explicit save error.
- Keyring write fails: row is rolled back or marked incomplete, with the exact
  vault error.
- Rollback delete fails: the failure is surfaced, not swallowed.
- Successful add: row remains, key is stored, dialog closes, active connection
  switches only after success.

## Acceptance

- A new provider never disappears unless the user explicitly deletes it or the
  database insert itself failed.
- Every failure names the step and shows the provider's raw error.
- A provider whose `/models` endpoint is missing can still be added and used for
  chat.
