# v0.8.1 plan: skills system and sandbox toolchain

Status: target. Follows v0.8.0. Source: `BUILTIN_SKILLS_AND_SANDBOX_SPEC.md`
(2026-10-31), phases 1 and 2 only.

0.8.1 ships the harness the built-in skills will sit on, not the two skills.
`pdf-workbench` and `deck-builder` come after, against this contract. The
release is versioned 0.8.1 by decision on 2026-10-31 even though it adds
features; it is the next release after v0.8.0.

## Scope

In:

1. Skills loader v2: our frontmatter schema, built-in and user folders, enabled
   state, `skill` tool integration.
2. `skills doctor`: tool and import checks inside the sandbox, golden tests when
   a skill declares them, JSON result.
3. Settings > Skills: list, enable/disable, version, self-test, open folder.
4. Sandbox toolchain: profiles, derived image build, pinned Python and Node
   packages, `lo-convert`, install blocking, repair.

Out: `pdf-workbench`, `deck-builder`, `docx-writer`, `xlsx-sheets`, `csv-clean`,
artifact/file cards, `read_document`, licenses page entries for the new
components. Those ride on 0.9.0 or later.

## Decisions

- **Provisioning happens at image build time.** The existing sandbox already
  builds one derived image from a sha-pinned Debian base and runs every command
  with `--network none`. 0.8.1 keeps that: the profile's packages are installed
  by `docker build`, the resulting image is what `sandbox_run` uses, and the
  runtime never has network. There is no first-run provisioning with temporary
  network.
- **Profiles replace free-form growth.** `core`, `office` (default) and `full`
  select apt, Python and Node package sets. The existing extra apt packages stay
  additive on top of the profile.
- **Pinned toolchain files.** `src-tauri/resources/sandbox/requirements.txt`
  pins Python with SHA-256 hashes, `package.json` + `package-lock.json` pin
  Node, and both are embedded in the Rust build. The image tag includes a hash
  of those files plus the profile and apt list, so changing a pin builds a new
  image instead of reusing a stale one. Apt package versions follow the pinned
  Debian base; exact apt pinning is deferred.
- **Skill folders are mounted into every sandbox run** read-only at
  `/opt/skills` and `/opt/skills-user`, which is what lets the self-test run in
  the same runtime as the skill's scripts.
- **Skills never widen permissions.** `skill` stays a read-only tool behind the
  same permission check. Scripts run through `sandbox_run` and its approval
  tier. The skill folders are mounted read-only and are protected write paths.
- **Windows host, Linux sandbox.** Skills execute inside the container. The
  `skills doctor` checks therefore run inside the same container, not on the
  host. Paths written by a skill are project-relative.

## Skills contract

Frontmatter (our schema; `description`, `name` and the first-line fallback stay
supported so old user skills keep loading):

```yaml
---
id: pdf-workbench
title: PDF Workbench
version: 1.0.0
triggers: ["pdf", ".pdf", "merge pdf"]
requires_tools: [python3, pdftotext, qpdf, tesseract]
requires_imports: { python: [pypdf, pdfplumber], node: [] }
network: none
writes: ["outputs/"]
summary: One sentence shown in the skill index.
---
```

- `skills_list` returns every discovered skill with source (`builtin` or `user`),
  enabled state, title, version, summary and the declared requirements.
- `skills_read` returns the raw `SKILL.md`, for Settings and future reference
  reading. `skill_read` keeps returning the model-wrapped block.
- `skills_set_enabled` persists disabled ids in `<app data>/skills.json`. A
  disabled skill disappears from the tool index and the tool refuses it.
- Discovery order: bundled resource `skills/`, then `<app data>/skills/`. A user
  skill with the same id shadows the bundled one, matching today's behavior.
- `skills_doctor` runs in the sandbox when it is ready. Without a sandbox it
  returns `{ok: false, detail: "sandbox is off"}` instead of probing the host;
  the host cannot prove the runtime a skill will actually use.
- Doctor result: `{ok, skill, missing[], failed_tests[], versions{}}`. Golden
  tests are `tests/run.sh` at the skill root, executed with the skill directory
  mounted at `/opt/skills/<id>:ro` and a scratch `outputs/` folder.
- `missing_tool` is the error code a skill reports when a declared tool is
  absent. Skills never install anything.

## Sandbox contract

- `SandboxConfig` gains `profile` (`core` | `office` | `full`, default
  `office`). Existing configs without it read as `office`.
- The Dockerfile installs, in order: baseline apt packages, profile apt
  packages, the pinned Python set in `/opt/venv`, the pinned Node set in
  `/opt/node-tools`, `lo-convert`, then `fc-cache -f`.
- `lo-convert <input> <outdir> [pdf|pptx|docx|xlsx]` is a shell script in the
  image. It uses a private profile per job, `--headless --norestore`, a 60 s
  default timeout, kills the process group on timeout, and serialises
  conversions with `flock`. Skills never call `soffice` directly.
- `sandbox_run` rejects commands whose parsed segments invoke `pip install`,
  `pip3 install`, `python -m pip install`, `apt`, `apt-get`, `npm install`,
  `npm i`, `pnpm add` or `yarn add`, unless the project config has
  `allow_installs` on. Rejection happens before the container starts.
- Repair = rebuild. `sandbox_rebuild` re-reads the lockfile and rebuilds when the
  profile, pins or Dockerfile hash changed; the UI button already exists.
- Disk guard: refuse `enable`/`rebuild` when the Docker data root has less than
  8 GB free, and clean apt/pip/npm caches inside the same layer.

## Work breakdown

1. **Loader and doctor** (this PR): `skills.rs` schema, discovery, enabled
   state, `skills_list`, `skills_read`, `skills_set_enabled`, `skills_doctor`,
   tests. `skill_index`/`skill_read` respect disabled state.

3. **Toolchain lock and image**: profile field, lockfile, Dockerfile, image tag

4. **Run guard**: install blocking with parsed segments and tests.
5. **Sandbox UI**: profile selector, size estimate, rebuild copy.
6. **Docs and release**: `docs/features.md` status, `docs/releases/v0.8.1.md`,
   `src/lib/releasenotes.ts`, version bump in the five manifests, clean-machine
   run.

## Verification

- `npx tsc --noEmit`, `npm test`, `npm run build`.
- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
  `cargo test`.
- `skills_doctor` green for a fixture skill whose `requires_tools` exist.
- With `allow_installs` disabled, a direct `sandbox_run` command containing
  `pip install` is refused by the install guard. The guard does not inspect the
  contents of a script that `skills_doctor` or a skill runs.
- Rebuild with an unchanged lockfile reuses the image; a changed pin produces a
  new tag and a rebuild.
- No skill file or script copied from the uploaded Anthropic material; the
  reference files are not part of the repo.

## Deferred from phases 1-2

- Exact apt version pinning. The base image is digest-pinned; apt follows that
  release at build time. Python and Node are hash/version pinned.
- A provisioning log dialog and the 8 GB free-space guard. Enabling shows the
  existing spinner, and Docker reports its own disk errors.
- License entries for poppler, qpdf, LibreOffice, the Python packages and the
  Node packages.
- Golden fixture PDFs/PPTX are generated by the future skill tests, not checked
  in as binaries.
- `allow_installs` is in the sandbox config with a Settings toggle; the approval
  card wording from the spec is not implemented.
