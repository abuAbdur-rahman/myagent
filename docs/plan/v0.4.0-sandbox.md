# v0.4.0 S1 — Sandbox plan (rev 2)

Implements `docs/releases/v0.4.0.md` S1. Rev 2 folds the owner's revised
plan (Docker only, host file tools, checkpoint + receipt) and the
corrections found when it was checked against the code.

## Summary

Docker stays the runtime, but the container is no longer treated as the
whole boundary: the writable project folder is the real attack path, so
this revision protects it and shrinks the container surface to one tool,
`sandbox_run`.

What changed from rev 1:

- Sensitive project paths (`.git`, `.vscode`, `.husky`, `.github`) are
  mounted read-only, along with agent-config files, and every exec ends
  with a receipt of changed config/hook files.
- A git checkpoint is taken before every exec, so `rm -rf .` is
  recoverable even though undo UI waits for v2.
- M1 is a UX shortcut for auto-allow. The container is the security
  boundary.
- Exec is ephemeral (`docker run --rm`) and killed with `docker kill`,
  because killing `docker exec` leaves the process running.
- File read, write, edit and delete move to the host with a path jail.
  Only code execution enters the container.
- `run_powershell` (D7) keeps the host and in sandbox mode becomes
  inspection-only: harmless, non-updating queries (time, disk, biggest
  files, process and network state). Anything that creates, updates or
  deletes files, or runs project code (js, python), is refused with a
  reason and routed to the sandbox.

Answers to the three open questions:

| Open question | Decision | Why |
| --- | --- | --- |
| Runtime: Docker or WSL2 direct | Docker Desktop. WSL2 direct is dropped. | WSL2 shares one VM with the dev distro, so network-off is VM-wide or not a real boundary. See Runtime pick. |
| Image delivery | Pull a pinned base on enable, then build one local derived image. No bundled tar. | Setup is host-side with consent; a tar adds 150MB+ to the installer and goes stale. |
| Package UX | Checklist for curated extras, locked baseline on top, text box under Advanced. | A checklist shows size before consent; free text covers the long tail. |
| File refresh (VERIFY cheapest) | Refresh the file tree when an exec exits. No watcher in 0.4.0. | Zero idle cost, and the host is the only other writer. |

## Runtime pick

Use Docker Desktop with the WSL2 backend. Ship it as the only runtime in
0.4.0 and refuse to enable when it is missing; never fall back to host
exec.

Why WSL2 direct loses on this machine class:

- All WSL2 distros share one utility VM and kernel. `networkingMode=none`
  in `.wslconfig` is VM-wide, so it would also cut internet from the dev
  distro.
- Per-process `unshare -n` works, but then the isolation is a convention
  inside a shared VM, not a boundary you can prove with a test.
- A distro imported for the sandbox can be reached from other distros and
  from Windows through `\\wsl$`, which widens the surface.

Docker's cost is memory on a 2015-era laptop, so measure before shipping.
Run this benchmark on the target machine and record the numbers in the PR:

| Measure | How | Pass |
| --- | --- | --- |
| Idle memory | Task Manager, `vmmem` with Docker Desktop running and no containers | Under 1.5GB |
| Cold exec latency | `docker run --rm --network none img true`, median of 10 | Under 2s |
| Bind read speed | `rg -c foo` over a 20k-file project through the bind | Within 3x of host rg |
| Soak | 10 minutes of back-to-back small execs | No leaked containers, flat memory |

Decision rule: if cold latency is 2s or more, switch to one long-lived
container per session with `docker exec`, plus an in-container `timeout`
and a kill of the process group on cancel. That fallback changes the
lifecycle rows of the test table (a kill leaves the container running),
so run the benchmark and the soak before freezing the design. If idle
memory is over 1.5GB, keep the feature but default the caps to 1 CPU and
1g and show the cost in Settings copy.

## Isolation contract

Every exec is one `docker run` with the flags below; the Rust side builds
this argument list and nothing else may start a container.

```
docker run --rm --name myagent-<execId> --label myagent.sandbox=1 \
  --network none \
  --read-only --tmpfs /tmp:rw,size=256m \
  --user 1000:1000 --cap-drop ALL --security-opt no-new-privileges \
  --env HOME=/tmp \
  --memory <mem> --memory-swap <mem> --cpus <cpus> --pids-limit 256 \
  -v <vmProjectDir>:/work:rw \
  -v <vmProjectDir>/.git:/work/.git:ro \
  -w /work <image@sha256:digest> timeout <secs> sh -c <cmd>
```

Rules:

- Network: none. Prove it with a test that opens a socket from the
  baseline `python3` (see Tests and gate — `curl` is not in the image).
- Filesystem: one project bind, with sensitive subpaths overlaid
  read-only (next section). No home, vault, DB or Docker socket.
- Secrets: no secret env at all. BYOK keys stay on the host; sandbox code
  that needs one calls a host tool that asks permission. `--env HOME=/tmp`
  is not a secret; it exists because `--user 1000:1000` plus a read-only
  rootfs leaves no writable home, which breaks git, pip and npm.
- Windows paths: the host path must be translated to the Docker
  Desktop/WSL2 form before it reaches `-v` and `-w` (`D:\oss\myagent` →
  `/run/desktop/mnt/host/d/oss/myagent`). A wrong translation mounts an
  empty directory and the exec silently runs against nothing, so every
  exec starts with a preflight: `test -f /work/<known project file>`; on
  failure, fail closed with "project folder not visible inside the
  container".
- Defaults scale to the host: `cpus = min(2, cores/2)`, `mem = 1g` on
  8GB machines or less, `2g` above. Both stay tunable in Settings.
- `--memory-swap` equal to `--memory` disables swap, so a runaway process
  is OOM-killed instead of thrashing a laptop disk.
- `--pids-limit` contains fork bombs, `--cap-drop ALL` and
  `no-new-privileges` contain privilege tricks, and the non-root user plus
  read-only rootfs contain a compromised interpreter.
- The image is referenced by digest, never by a moving tag. A failed
  rebuild keeps the previous digest.

## Project-dir protection

The container cannot reach the host, but whatever it writes into the
project is later executed by the host (git hooks, `vite.config`,
`package.json` scripts). Three controls close that path.

1. **Read-only overlays.** Mount `.git`, `.vscode`, `.husky` and `.github`
   read-only on top of the rw bind, plus the agent-config paths that steer
   the next session: `AGENTS.md`, `CLAUDE.md`, `.mcp.json`, `.claude/**`,
   and the app's own `skills/` and `commands/` folders. Missing
   directories are skipped, not created.
2. **Pre-exec checkpoint.** Before each exec in a git repo, snapshot the
   tree and store the commit under `refs/myagent/pre-exec/<execId>`. It
   takes milliseconds and leaves the working tree untouched.
   `git stash create` alone is not enough — measured on git 2.54,
   `git stash create` captures tracked changes only, and `create -u` is
   accepted but still ignores untracked files, so an untracked file
   written by the previous exec would be unrecoverable. Use a temporary
   index outside the worktree:

   ```
   GIT_INDEX_FILE=<temp> git read-tree HEAD
   GIT_INDEX_FILE=<temp> git add -A
   tree=$(GIT_INDEX_FILE=<temp> git write-tree)
   commit=$(git commit-tree $tree -p HEAD -m "pre-exec <execId>")
   git update-ref refs/myagent/pre-exec/<execId> $commit
   ```

   A clean tree returns no stash commit, so fall back to `HEAD`. Restore
   is `git checkout <ref> -- .` (undo UI is v2; only the data is kept
   now). Prune: keep the newest 50 refs per project, prune on startup.
   Outside a git repo, warn once in Settings copy that edits are final.
3. **Sensitive-change receipt.** After exit, compare the tree against the
   checkpoint and list changed files that match: `*.config.*`,
   `package.json`, lockfiles, `Makefile`, `*.sh`, `.env*`, CI files, the
   agent-config paths above, and anything newly marked executable. Show
   them on the exec receipt with a one-click review. Never auto-open or
   run them.

Host-side rules for the same reason:

- Path jail: canonicalize every path, require it to stay under the project
  root, and reject symlinks, junctions and reparse points that resolve
  outside it. Implementation note: canonicalize the parent directory and
  compare with `Path::starts_with` on the canonicalized root; on Windows
  open files with `FILE_FLAG_OPEN_REPARSE_POINT` semantics or re-check
  after the handle is open.
- Host read, write, edit and delete tools never follow a link created by
  sandbox code.
- Writes to the overlaid paths above are refused on the host side too,
  with a clear reason, so the agent cannot sidestep the mount.

## Exec lifecycle and tools

One container tool, `sandbox_run`; file operations stay on the host, where
a path jail is cheaper and faster than a round trip through a 9p bind.

| Tool | Runs on | Notes |
| --- | --- | --- |
| `sandbox_run(cmd, cwd, timeout)` | Container | The only tool that starts a container. Covers python, node, rg, sed, grep. |
| `sandbox_read`, `sandbox_glob`, `sandbox_grep` | Host | Native Rust (`ignore` + regex), jailed to the project root. |
| `sandbox_write`, `sandbox_edit`, `sandbox_delete` | Host | Jailed, refuse protected paths, checkpoint first. |
| `run_powershell` (existing D7) | Host | In sandbox mode: inspection only — time, disk, largest files, process and network state. No create, update, delete or project-code run. |

Lifecycle of one `sandbox_run`:

1. Check daemon state; if down, fail closed with a Start Docker action.
2. M1 screen (see Permission model), then take the git checkpoint.
3. Preflight the bind (`test -f /work/<known project file>`), then
   `docker run --rm --name myagent-<execId>` with a `timeout` wrapper
   inside, so the process dies even if the host loses the CLI.
4. Stream stdout and stderr as `SandboxEvent` over the existing Channel.
   Send the output through D13: cap the in-context part (32KB, head and
   tail), write the full stream to a spill file, and include the path and
   the cut markers in the result.
5. Cancel and timeout call `docker kill myagent-<execId>`, with
   `docker rm -f` as a fallback if the kill does not return. Killing the
   `docker` client alone does not stop the process inside.
6. On exit, write the audit row, prune old checkpoint refs, run the
   sensitive-change receipt, refresh the file tree.
7. On app start, remove containers labelled `myagent.sandbox=1` left by a
   crash.

Ephemeral containers cost one cold start per call but share no state
between calls, which is what makes the behavior easy to reason about.
Files persist through the bind.

## Permission model

Toggle ON sets permission mode `sandbox` (D6). In that mode `sandbox_run`
and the jailed project file tools auto-allow after the M1 screen passes;
every host call outside the project still asks.

M1 is a UX shortcut, not the boundary. A model can be fooled by
`python -c` obfuscation, so a pass from M1 means "skip the prompt", never
"safe". The container flags and the project protections carry the
security. If M1 is not available, the toggle is disabled with a reason
(no screen, no auto-allow), because the release order is M1 → S1.

Where the mode plugs in: `permissions::check` already consults
`mcp::policy` and then the per-project rules. Add the sandbox mode as
another policy provider at that seam. Precedence: an explicit `Deny` rule
and a protected path beat sandbox auto-allow. `check` already defaults to
`Ask` on error; keep it.

What M1 screens, and what it stops screening:

| Screen | Why |
| --- | --- |
| Mass deletion or overwrite of the project (`rm -rf .`, `rmtree('.')`, `find -delete`, `> *`) | The one destructive act the container cannot contain, since the bind is writable. |
| Writes aimed at protected paths (`.git`, hooks, CI, `.env`, agent config) | Defence in depth over the read-only overlays. |
| Attempts to read secrets (`env`, `/proc/*/environ`) | Should return nothing, but flag intent. |
| `rm -rf /`, `mkfs`, fork bombs, outbound sockets | Dropped. The read-only rootfs, pids limit and no-network flags make these harmless, and asking about them is accept-fatigue. |

Behavior: a flagged command becomes an Ask card with the reason and the
checkpoint ref. M1 errors, timeouts or an unparseable verdict also become
an Ask, never a silent allow. If Docker is down, fail closed: no exec and
no host fallback.

Audit: one `log_audit` row per exec with tool, truncated command, exit
code, duration, checkpoint ref and whether M1 passed or the user approved
(pack the extra fields into `detail`, or add a migration; the table has
`id, ts, conversation_id, tool, decision, detail` today).

## Image, packages and file refresh

**Image delivery: pull on enable, then build locally.** Enable is the one
moment network is allowed, and it is host-side with consent.

1. Show the download size and the package list, and wait for an explicit
   Enable click.
2. `docker pull debian:bookworm-slim@sha256:<pinned>`. Docker resumes
   layers, which matters on unstable power and data.
3. `docker build` a derived image `myagent-sandbox:<hash>` that installs
   the baseline and selected extras, after which nothing touches the
   network again.
4. Store the resulting image digest; all runs reference it. A Rebuild
   button reruns steps 2 and 3 when the package list changes, and keeps
   the old digest on failure.

A bundled tar is rejected: it adds 150MB+ to every installer and ages with
each security fix. Offer `docker load` from a file as an Advanced option
for machines that cannot pull.

**Distro.** Ship one pinned `debian-slim`. Alpine's musl breaks many
Python wheels, and a picker adds states with no benefit. Revisit only if
there is a concrete need for Ubuntu.

**Package UX: checklist plus Advanced text.**

- Locked baseline shown greyed and checked: python3, node, ripgrep, sed,
  grep, coreutils, findutils. `git` is not in the baseline: the `.git`
  overlay is read-only, so write commands fail on `index.lock`; add it
  only if a read-only workflow proves useful.
- Optional extras as a checklist with size beside each (for example numpy,
  pandas, typescript, jq). Total download size updates live.
- Advanced: a text box of apt and pip package names for the long tail,
  validated against a character allowlist before the build.

**File refresh (cheapest).** Refresh the project tree once when each exec
exits, and after host-side edits. A filesystem watcher is not needed in
0.4.0: the host is the only other writer, and exec boundaries are exactly
when files change. Revisit a `notify` watcher with a 200ms debounce only
if users run long background commands.

## Tauri wiring and Settings states

New `src-tauri/src/sandbox.rs`, using the existing Channel pattern from
`chatStream` and the `StreamState` cancel registration reuse.

- `sandbox_status` returns one of `not_installed`, `daemon_stopped`,
  `no_image`, `ready`, plus image size, digest and Docker version.
- `sandbox_enable(packages)` runs consent, pull, build and verify,
  streaming progress events.
- `sandbox_run(cmd, cwd, timeout)` streams
  `SandboxEvent { stdout, stderr, exit }` and returns the checkpoint ref
  and the sensitive-change list.
- `sandbox_rebuild`, `sandbox_disable` and `sandbox_reap_orphans` (also
  called at startup).
- In `tools.rs`, `approval_resources` returns the project-relative path or
  the command, and `check()` auto-allows only sandbox-scoped calls after
  M1 passes.

Settings has one page with a single toggle whose state explains itself.
The toggle is disabled with a reason and one action in each blocked state:

| State | Toggle | Action shown |
| --- | --- | --- |
| `not_installed` | Disabled | Link to install Docker Desktop, with a Recheck button |
| `daemon_stopped` | Disabled | Start Docker, then Recheck |
| `no_image` | Enabling | Download size, package checklist, Enable button |
| `ready` | On | Caps, packages, Rebuild, exec log |

Copy to include: off by default; no internet inside; only this project
folder is visible; checkpoint is kept for git projects; edits are final
outside git; the host shell stays inspection-only while the sandbox is on.

## Tests and gate

Each row is a test that must exist and pass before S1 merges; new cases in
this revision are marked. Container rows need Docker, which CI does not
have (`.github/workflows/ci.yml` runs on `windows-latest`, and hosted
Windows runners cannot run Linux containers; the dev box is Windows
without Docker too). Ship them as `#[ignore]` tests selected by
`MYAGENT_SANDBOX_IT=1` and run them on the target machine before merge;
everything else (jail, flag builder, receipt matcher, M1 verdict parsing,
Settings states) is a normal unit or vitest test and stays in CI.

| Area | Test | In CI | New |
| --- | --- | --- | --- |
| Network | A `python3` socket connect inside the container fails; egress is zero (`curl` is absent from the image, so it cannot prove anything) | No | Yes |
| Filesystem | Only the project is host-backed: a host path under `/run/desktop/mnt/host/...` is not reachable, and `..` escapes from `/work` fail. The container's own `/etc/passwd` exists by design, so compare it with the host's instead of asserting absence | No | Yes |
| Bind preflight | A wrong or unshared project path fails closed with "project folder not visible" instead of running on an empty tree | No | Yes |
| Protected paths | Writing `.git/hooks/x` from the container fails; host tools refuse it too | No | Yes |
| Agent config | Writing `AGENTS.md` and `.mcp.json` from the container fails and appears in the receipt | No | Yes |
| Links | A symlink or junction created by sandbox code is not followed by host tools | Yes | Yes |
| Secrets | `env` and `/proc/self/environ` inside the container hold no keys | No | Yes |
| HOME | `python3` and `node` can write a file and `pip` can install offline with the caps in place | No | Yes |
| Caps | Memory limit kills an allocator; CPU cap holds; no swap | No | Yes |
| Fork bomb | `pids-limit` contains it and the host stays responsive | No | Yes |
| Timeout and cancel | After kill, `docker ps` shows no container and the process is gone | No | Yes |
| Output flood | `yes` is capped with a spill-file path and visible cut markers | Yes | Yes |
| Checkpoint | After `rm -rf .`, the ref restores the tree, including a file that was untracked before the exec | No | Yes |
| Receipt | Modifying `package.json` appears in the sensitive-change list | Yes | Yes |
| Orphans | A killed app leaves a labelled container; the next start removes it | No | Yes |
| M1 | Mass-delete command surfaces an Ask card; a screen error fails closed; a Deny rule beats sandbox auto-allow | Yes | |
| Host shell split | In sandbox mode `run_powershell` allows an inspection command and refuses a file-writing one with a reason pointing at the sandbox | Yes | Yes |
| Daemon down | Exec is refused with no host fallback | No | |
| Audit | Exactly one row per exec with checkpoint ref | Yes | |
| Vitest | Toggle persists, state-specific disabled reasons, exec log renders, flagged command shows Ask card | Yes | |

Gate: `npx tsc --noEmit`, `cargo fmt --check`,
`cargo clippy --all-targets -- -D warnings`, `cargo test`,
`fallow dead-code`, vitest — all in CI. Container rows with
`MYAGENT_SANDBOX_IT=1`, the benchmark table from Runtime pick, a 10-minute
exec soak, and a host leak audit of processes, network and filesystem —
on the target machine, recorded in the PR.

## Implementation notes (v0.4.0)

Measured on the target machine (Docker Desktop 4.96.0, WSL2 2.7.11,
16 GB / 4 cores):

| Measure | Result | Decision |
| --- | --- | --- |
| Cold exec latency | 1.08 s median of 10 (`docker run --rm --network none`) | Keep ephemeral `docker run --rm` |
| Idle WSL memory | ~3.1 GB with Docker Desktop running | Default caps to 1 CPU / 1 GiB, shown in Settings copy |
| Bind | `-v D:\…:/work` works; preflight passes | Keep the bind, no path rewriting |

Shipped in `src-tauri/src/sandbox.rs`:

- `sandbox_status`, `sandbox_enable`, `sandbox_disable`, `sandbox_rebuild`,
  `sandbox_reap`, `sandbox_set_limits`.
- Config lives in `app_data_dir/sandbox.json` (off by default).
- Image: pinned `debian@sha256:7c7b2c…` pulled on Enable, derived image
  tagged from the package list and stored by image ID; the fast path
  re-enables without rebuilding when the package list is unchanged.
- One ephemeral container per call with every flag from the isolation
  contract; `\\?\` verbatim paths are stripped before they reach `-v`.
- Checkpoint (`refs/myagent/pre-exec/<id>`) uses a temp index and keeps 50
  refs; restore is `git checkout <ref> -- .` (verified: an untracked file
  survives `rm -rf` and comes back).
- Receipt from `git diff-tree` between the checkpoint tree and a post-run
  tree, plus newly executable files.
- Host tools `sandbox_read`, `sandbox_glob`, `sandbox_grep`,
  `sandbox_write`, `sandbox_edit`, `sandbox_delete` with a canonicalized
  jail (rejects `..`, absolute paths, reparse points and protected paths).
- Settings → Sandbox page with the four states, folder picker (plugin
  dialog), extras checklist, Advanced package box, limits, Rebuild.

Deviations from the rev 2 sketch, recorded so they are not silent:

- Tool output is collected and capped (D13 spill) instead of streamed as
  `SandboxEvent`: model tools have no per-call event channel today, and
  adding one is a larger refactor. Cancellation still kills the container.
- The exec log is the existing Audit page (one row per exec, decision
  `allow`, detail carries exit, duration, checkpoint and receipt), not a
  separate list inside Settings.
- `sandbox_disable` keeps the image for a fast re-enable (open question
  resolved that way for now).
