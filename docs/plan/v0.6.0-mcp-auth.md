# v0.6.0 — MCP authorization and Streamable HTTP

> The current MCP client speaks protocol `2024-11-05`, posts plain JSON, and has
> no authorization. An online MCP server almost always requires OAuth, so today
> the only reliable path is a local stdio bridge. 0.6.0 replaces the transport and
> session layer with the official Rust SDK, `rmcp` 3.7.0, and adds real OAuth 2.1
> with a persisted token store.
>
> **Shipped scope.** 0.6.0 ships DCR, PKCE S256, a `127.0.0.1` loopback
> callback, refresh and local disconnect. Pre-registered clients,
> `myagent://` callbacks, server-side revocation, a DPAPI fallback and the mock
> OAuth integration test are deferred. The sections below keep the full design;
> deferred items are marked.

---

## 1. Why 0.6.0

`src-tauri/src/mcp.rs` is wrong at three layers:

1. **Protocol.** It sends `2024-11-05` initialization over a plain POST. Modern
   servers use Streamable HTTP (`2025-03-26`, `2025-11-25`, `2026-07-28`): POST
   with `Accept: application/json, text/event-stream`, `MCP-Protocol-Version`,
   `Mcp-Session-Id` where the version still has sessions, and an
   `notifications/initialized` message.
2. **Authorization.** It has no bearer token, no OAuth discovery, no 401
   challenge handling. An online server that answers `401` is a dead end.
3. **Lifecycle.** No protected-resource metadata, client registration, PKCE,
   token refresh or revoke.

The result is that "online MCP" only works through a third-party stdio bridge
such as `npx -y mcp-remote <url>`. That is a workaround, not a product.

This is a new capability, not a fix for a shipped feature, so it is 0.6.0.

---

## 2. Decisions

| Decision | Choice |
| --- | --- |
| Engine | `rmcp` 3.7.0, official Rust SDK |
| Protocol | `2026-07-28` with `2025-11-25` and legacy fallback |
| OAuth | OAuth 2.1, PKCE S256, RFC 9728 discovery, DCR (pre-registered client deferred) |
| Callback | Loopback `127.0.0.1` only; custom scheme deferred |
| Token storage | `CredentialStore` backed by Windows Credential Manager |
| UI auth modes | None, Bearer token, OAuth 2.1 |
| Existing config | Keep the table, policy, approvals and tool namespacing |

`rmcp` 3.7.0 is the current release and implements the `2026-07-28` and
`2025-11-25` specs. It is MSRV 1.88; the project is on 1.96. CVE-2026-63127
(missing RFC 9728 resource validation) and CVE-2026-64684 were fixed in 2.0.0
and 2.1.0; 3.7.0 is above both. Pin the minor and review the lockfile on every
update.

CIMD is not the default. CIMD requires the client to host a metadata document at
a stable HTTPS URL; MyAgent has no such endpoint yet. Dynamic client registration
covers the providers that matter now. Pre-registered client id/secret and CIMD
are follow-ups; providers that reject DCR are not covered in 0.6.0.

| In 0.6.0 | Out |
| --- | --- |
| `rmcp` stdio + Streamable HTTP transports | MCP server mode |

| Protocol negotiation and legacy SSE fallback | Non-Windows platforms |
| Key rotation (already promised for 0.6.0) | Judge model, sandbox/YOLO, recent models, OpenCode |

The judge model and the other deferred items stay in their own plans. This
document covers MCP only; key rotation is listed because it is already committed
to 0.6.0 and touches the same settings surface.

## 4. Current code and the seam

Keep:

- `McpServerConfig`, the `mcp_servers` table, `row_policy`, `spec_for`,
  `try_execute`, tool namespacing, approvals, timeout and audit.
- The `McpState.sessions` map, so a connected session is reused.

Replace:

- `ActiveTransport` (hand-rolled stdio and HTTP/SSE).
- `connect_once`, `initialize_session`, `sse_request` and the JSON-RPC id
  bookkeeping.
- The probe cache's transport assumptions.

New shape:

```text
McpState
  sessions: HashMap<key, Arc<Mutex<RunningService>>>
  pending_auth: HashMap<server_id, AuthTask>
  probe_cache: as today

McpSession
  service: RunningService
  tools: Vec<McpToolDef>
  auth: AuthKind
```

`rmcp` exposes `RunningService` with `list_tools` and `call_tool`. The adapter
maps its `Tool` values into the existing `McpToolDef` so the rest of the app does
not change.

## 5. OAuth flow

### 5.1 Discovery

1. Connect to the MCP URL; on `401`, read `WWW-Authenticate` for
   `resource_metadata`.
2. Fetch protected-resource metadata (RFC 9728), including `resource` and
   `authorization_servers`.
3. Fetch authorization-server metadata (RFC 8414 / OIDC discovery).
4. Use the advertised registration method: CIMD when supported and configured,
   otherwise DCR, otherwise a pre-registered client.

`rmcp`'s `OAuthState` and `AuthorizationRequest` own this sequence. MyAgent
supplies the HTTP client, the callback URI and the credential store.

### 5.2 Callback

Loopback only in 0.6.0:

- Bind `127.0.0.1:0`, use `http://127.0.0.1:<port>/callback` as the exact
  redirect URI, wait up to five minutes, validate `state`, exchange the code.
- A `localhost` fallback and the `myagent://oauth/callback` custom scheme are
  deferred. Providers that reject the IP literal are not covered in 0.6.0.

The listener is bound before registration so the redirect URI is exact. A cancel
button aborts the listener and drops the pending `OAuthState`.

### 5.3 Tokens

`CredentialStore` key: `mcp-oauth:<server-id>`.

- `load` returns `None` when no credential exists.
- `save` serializes `StoredCredentials` and writes it to the Windows Credential
  Manager.
- If the blob exceeds the 2560-byte Credential Manager limit, split it across a
  small manifest plus chunks. A DPAPI file fallback is deferred.
- `clear` removes the credential and any chunks, including orphans left by a
  corrupt manifest.

No token ever enters the webview. The MCP page shows only `Connected`,
`Authorization required`, `Expired` or `Reconnect`.

`AuthClient` adds `Authorization: Bearer …`, refreshes before expiry, and turns a
`401` into `AuthorizationRequired`. A definitive `invalid_grant` clears the store
and moves the server to `Reconnect`.

### 5.4 Authorization states

```text
none -> connecting -> connected
                 \-> auth_required -> authorizing -> connected
                 \-> failed
connected -> expired -> auth_required
```

Only `auth_required`, `failed` and `expired` are user-visible. The probe result
keeps the tool list from the last good session until a new one succeeds.

## 6. Bearer auth

For servers that issue a PAT or API key:

- `auth_type = 'bearer'`;
- the token is stored in the vault under `mcp:<server-id>`;
- the transport sends `Authorization: Bearer <token>`;
- the UI never reads the token back, only `has_token`.

This covers GitHub, Sentry, Stripe and similar servers without an OAuth dance.

## 7. Schema and migration

Migration 30:

```sql
ALTER TABLE mcp_servers ADD COLUMN auth_type TEXT NOT NULL DEFAULT 'none';
```

- Existing rows become `none`; their current URL/SSE behaviour is preserved.
- `transport` accepts `stdio`, `http`, `sse`. `http` is Streamable HTTP; `sse`
  stays as the legacy `2024-11-05` path.
- New rows default to `http` for a URL and `stdio` for a command.
- No token, client secret or header value is stored in SQLite.

If custom headers are added later, they go in the vault as a JSON blob, not in
the table.

## 8. UX

MCP server dialog:

- Name, transport, command or URL.
- Auth: `None` / `Bearer token` / `OAuth 2.1`.
- Bearer: password field, "Save token", "Clear token".
- OAuth: "Save first", then "Connect" (registration happens on first connect),
  "Reconnect", "Disconnect".
- Status line: `Not connected`, `Connecting…`, `Waiting for browser…`,
  `Connected (N tools)`, `Authorization required`, `Expired`, `Failed: …`.
- Cancel while waiting.

MCP page:

- Probe state per server, with "Reconnect" and "Edit".
- Edit opens the dialog for the auth mode and token actions.
- No token values, no client secrets, no raw callback URLs.

`mcp_test` is unchanged for stdio. For an online server, the draft must be saved
before OAuth can start, because the callback needs a stable server id and a
credential-store key. The dialog says so.

## 9. Security

- PKCE S256, `state`, exact redirect URI, five-minute callback timeout.
- RFC 8707 `resource` is preserved; a token minted for one resource is never sent
  to another host.
- `rmcp` 3.7.0 or newer; CVE-2026-63127 and CVE-2026-64684 are below the floor.
- Discovery URLs are HTTPS; loopback is the only HTTP exception.
- The token store is Windows Credential Manager, never SQLite, never JS.
- No token, code, verifier or client secret is logged.
- A `401` does not silently downgrade to an unauthenticated retry.
- Re-auth stores the new token only after the callback succeeds; disconnect
  clears the local token. Custom scheme callbacks are deferred.
- Tool approvals, deny rules and audit rows are unchanged.

## 11. Failure matrix

| Failure | Behaviour |
| --- | --- |
| Server returns 401 with no metadata | `auth_required`; show the server message |
| Discovery returns 404 | `failed`; link to the server's docs |
| DCR rejected | `failed`; pre-registered client is deferred |
| Loopback rejected | `failed`; custom scheme is deferred |
| Browser closed / timeout | `failed` after five minutes; token unchanged |
| State mismatch | Reject; log no secrets; require a new attempt |
| Token expired, refresh works | Refresh silently, retry once |
| Refresh `invalid_grant` | Clear token; `Reconnect` |
| Token store write fails | `failed`; do not mark connected |
| Blob too large for Credential Manager | Chunk or DPAPI fallback |
| Protocol version rejected | Negotiate down; legacy SSE last |
| Session id missing/expired | Re-initialize once, then surface |
| `rmcp` panics or returns a protocol error | `failed`; keep the old tool list |
| Cancel during authorization | Abort listener; clear pending state |

## 13. Accepted risks

- **DCR gaps.** Some providers require CIMD or a manually registered client.
  Pre-registered client support covers the latter; CIMD needs a hosted metadata
  URL and is deferred.
- **Loopback rejection.** A few providers require a fixed redirect or custom
  scheme. The custom-scheme fallback covers this, at the cost of installer
  registration.
- **Credential Manager limit.** The chunk/DPAPI path is extra code; it is tested
  with oversized fake credentials.
- **SDK churn.** `rmcp` is moving quickly. Pin the minor, review the lockfile,
  and keep the adapter tests independent of the SDK's internal types.
- **Binary size and build time.** The SDK brings `oauth2`, `reqwest 0.13` and
  `process-wrap`; the installer grows. Accepted for a tested OAuth stack.
- **Windows-only.** The token store and deep-link registration are Windows
  specific, matching the product.
