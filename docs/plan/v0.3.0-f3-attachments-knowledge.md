## Locked decisions
1. No vector DB. Grounding v1 = filename LIKE + keyword scan over stored text, fixed top-N files + fixed char budget. Reason: SQLite-only, full re-read waits for v2 file tools.
2. Budgets: 4k chars/file × 3 files/query. Reason: bounded context, OpenWebUI uses top_k=3 default.
3. File row = uuid + `sha256(bytes)` + path + extracted text + meta. Knowledge = `knowledge_docs` + join to project. Reason: OpenWebUI `File.hash` + `KnowledgeFile` join pattern, minus embeddings.
4. Store extracted text as sidecar files under `app_data/knowledge/{project_id}/{sha}.txt`, DB holds pointer + meta + excerpt. Reason: avoids SQLite bloat + PG-OOM class bugs (OpenWebUI caps LIKE with `RAG_FILE_CONTENT_SEARCH_MAX_CHARS`).
5. Excerpt wrap `<source name=file>text</source>`, single template with `{{CONTEXT}}`/`{{QUERY}}` appended to system message. Reason: OpenWebUI `rag_template` pattern.
6. Per-chat attachments vs project knowledge: both, same ingest, `chat_id` nullable (null = project knowledge). Reason: one pipeline, two scopes.
