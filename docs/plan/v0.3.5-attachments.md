# v0.3.5 S1 — Chat document attachments plan

Implements the slice after the v0.3.4 patch: attach documents in **any** chat,
extract their text locally, put that text in front of the model, and let the
model read more on demand. Extends `F3`; leaves `F4` (images) alone and keeps
`B11` (delete) honest.

## Summary

Today a non-image attachment requires a project (`Composer.tsx:251`, toast
"Select a project first to attach files."), only `text/*` plus
json/xml/js/ts are accepted, extraction is a UTF-8 decode in the renderer
(`knowledge.ts:93`), and the store is project-keyed
(`knowledge.rs:7` → `knowledge/<projectId>/<sha>.txt`). `knowledge_docs.chat_id`
exists but is never populated.

v0.3.5 makes a document attachment a first-class chat object: it is extracted in
Rust, stored once in a content-addressed store, referenced by the message (so
regenerate and edit-resubmit keep it), injected into the user turn as `<source>`
blocks, and readable on demand through a `read_document` tool.

## Decisions (owner-answered)

| Question | Decision | Why |
| --- | --- | --- |
| How text reaches the model | Whole extracted text in the **user message**, bounded, plus a `read_document` tool | Both references do exactly this pair: Open WebUI puts `<source>` in the last user message (`middleware.py:996-1007`), OpenCode inlines `Attached file: <name>` (`to-llm-message.ts:37-54`); both add an on-demand reader (`view_file`, `read`). Keeps the 6000-char system budget (`context.ts:5`) for project knowledge. |
| Formats | text/code family, html, pdf, docx, xls/xlsx/ods | Owner asked for more than PDF. Media (video/audio/gif/image) stays out: images already have the vision path. |
| Spreadsheets | In scope via `calamine` | Owner-answered "also spreadsheets". |
| Persistence | Doc refs live on the message, union with images in `messages.attachments` | Regenerate / edit-resubmit must keep the documents, exactly like images (`knowledge.ts:168`). No migration needed, the column is TEXT. |
| Caps | 10 MiB per file, 2 MiB stored text, 3 docs per message | Aligns with the existing 10 MiB image cap (`Composer.tsx:26`) and the 2 MiB sidecar cap (`knowledge.rs:5`). |
| Attach inside a project | Always chat-scoped, **plus a reference in the project bucket** | One copy of the bytes; the project Docs tab and project-wide knowledge still see the file. |
| Parser panics | Release `panic = "unwind"` + `catch_unwind` around extraction | `panic = "abort"` (`Cargo.toml:49`) would let a malformed PDF abort the app with no error surface. |
| Release | v0.3.5 | `v0.4.0` stays the sandbox (`docs/plan/v0.4.0-sandbox.md`). |

## Reference evidence (read-only, external)

`D:\oss\reference\claude` = Open WebUI, `D:\oss\reference\opencode` = OpenCode.

- Open WebUI extraction is per-format behind a loader: pypdf, docx2txt,
  BeautifulSoup, pandas/unstructured, python-pptx
  (`retrieval/loaders/main.py:517-818`). Full-context vs retrieval is chosen by
  `item.context == 'full'` or `BYPASS_EMBEDDING_AND_RETRIEVAL`
  (`retrieval/utils.py:1505-1542`); we have no embeddings, so full text is the
  only honest path.
- Open WebUI full-context is **uncapped** and re-sent every turn
  (`middleware.py:940-1007`, `Chat.svelte:3454-3463`). We bound it instead,
  because we know `modelContextLimit` per model and have no compaction
  equivalent beyond that.
- OpenCode inlines whole text attachments (20 MiB cap, `prompt.ts:203`), has no
  pdf/docx/xlsx extraction, sends PDF as provider media, and drops other binary
  formats silently (`to-llm-message.ts:82`) — a failure mode we refuse.
- OpenCode's reader: `read(path, offset, limit)`, `MAX_READ_LINES = 2000`,
  `MAX_READ_BYTES = 50 KiB`, per-line clamp 2000 chars, tail notice
  `[Output truncated. Continue reading with offset: <next>]`, binary refusal
  `Cannot read binary file: <resource>` (`tool/read-filesystem.ts:14-21`,
  `tool/plugin/read.ts:200-209`). Our tool copies this shape.

## Architecture

### 1. Storage — one copy, content addressed

- New store root: `<app_data>/documents/<sha256>.txt`, written through a new
  `src-tauri/src/documents.rs` (mirrors `knowledge.rs`: write/read/delete/wipe,
  2 MiB cap).
- `documents` is shared by chat docs and project docs, so the same bytes are
  never stored twice. Rows keep the `path` column; readers use the stored path
  when present and fall back to the legacy computed
  `knowledge/<projectId>/<sha>.txt`, so existing installs keep working with no
  data migration.
- Reference-counted delete: after removing rows, the caller asks for the shas
  still referenced by `chat_docs` **and** `knowledge_docs`; only unreferenced
  files are unlinked. Implemented as `documents_wipe_unreferenced(shas)` so a
  chat delete can never dangle a project reference.
- `wipeAll` removes the whole `documents` dir alongside `knowledge`.

### 2. Extraction — new `src-tauri/src/extract.rs`

`pub fn extract(name: &str, mime: &str, bytes: &[u8]) -> Result<ExtractedText, ExtractError>`
where `ExtractedText { text: String, pages: Option<u32> }` and `ExtractError`
carries a user-facing reason (`Unsupported("…")`, `NoTextLayer`, `TooLarge`).

| Input | Extractor | Note |
| --- | --- | --- |
| `text/*`, md, csv, json, yaml, xml, toml, sql, code, log | UTF-8 fatal decode + BOM strip + CRLF normalize | Today's behaviour, moved to Rust |
| html, htm, xhtml | `htmd` 0.5 (already a dependency) | Markdown out |
| pdf | `pdf-extract` 0.12 | Text layer only; empty result → `NoTextLayer` ("scanned PDF, OCR is not supported") |
| docx | `docx-rs` 0.4 | Paragraphs, heading levels, tables as rows |
| xls, xlsx, ods | `calamine` 0.36 | `## <sheet>` + rows, per-sheet and total cell caps |
| video, audio, gif, image, .doc, .ppt, odt, pptx, epub, msg, unknown | none | Explicit unsupported message, never a silent empty document |

Dispatch is mime first, extension second; unknown is a refusal, not a guess.
Extraction runs inside `tokio::task::spawn_blocking` wrapped in
`catch_unwind`, so a parser panic becomes a toast (see the panic decision).

### 3. Ingest path

Renderer reads `arrayBuffer()` (not `file.text()`, which mangles binary), caps
at 10 MiB, hashes with `crypto.subtle`, then:

1. `chatDocShaExists(conversationId, sha)` → duplicate toast, stop.
2. `api.attachmentIngest(conversationId, name, mime, base64)` → Rust extracts,
   writes `documents/<sha>.txt`, returns `{sha, chars, pages}` or a typed error
   the UI turns into "no text layer" / "not supported" / "over 10 MiB".
3. TS inserts the `chat_docs` row; a row failure rolls the sidecar back
   (mirrors `knowledge.ts:99-113`).
4. If a project is active, also insert a `knowledge_docs` row (project_id,
   `chat_id` now populated, same sha and path) unless `UNIQUE(project_id,
   sha256)` already has it.

### 4. Message refs and injection

- `types.ts`: `messageAttachmentSchema` becomes a discriminated union —
  `{kind:"image", dataUrl}` and `{kind:"doc", name, mime, sha256, chars}`;
  array stays capped at 12, with a separate cap of 3 docs.
- `parseMessageAttachments` keeps returning images for the existing callers
  (`turnContent`, `withFinalTurnImages`); a new `parseDocAttachments` feeds the
  document path, so nothing existing changes shape.
- Send path: the message stores the doc refs, and the outgoing user content
  gains the documents' text as
  `<source name="report.pdf" type="pdf">…</source>` blocks before the user's own
  text, bounded by `DOC_CHARS_PER_FILE` (40 000) and `DOC_CHARS_PER_TURN`
  (120 000, then trimmed proportionally). A trimmed document ends with
  `[truncated: <n> of <total> chars included, call read_document for more]`.
- Regenerate / edit-resubmit: `turnContent` becomes async-aware for docs by
  reading the stored text for the last user turn's refs, so the model sees the
  same content without the user re-attaching.

### 5. Reader tool `read_document`

- Spec: `read_document(name, start, max_chars, grep)`; `start` is a character
  offset, `max_chars` defaults to 20 000 and is clamped, `grep` reuses
  `tooltext::compile_grep` (same 512-char cap as `run_powershell`/`web_fetch`).
- Resolution: only documents referenced by the **current conversation** (chat
  docs, plus project docs when the chat is in a project), matched by name or
  sha; anything else is refused, so the tool can never read arbitrary paths.
- Output: the window plus `[showing <a>-<b> of <n> chars; call read_document
  with start=<b> for more]`; large output reuses the existing spill path.
- Gating: `tool_specs(include_describe_image, include_read_document)` — the tool
  is offered only when the conversation has documents, the same way
  `describe_image` is offered only with a vision fallback.
- Read-only and local, so it needs no approval prompt; it stays inside the
  existing tool loop, logging and step cap.

### 6. UI

- Composer: the project-only guard is removed; the paperclip accepts documents
  in any chat, with toasts for unsupported type, over 10 MiB, duplicate and no
  text layer. Chips show name, size and a per-file status, and are capped at 3.
- Transcript: a document card (icon, name, `Document · PDF`, size) matching the
  owner's reference shot `D:\oss\reference\images\03-chat-thread-with-document-card.png`.
- The project Docs tab is unchanged.
- Unsupported media is refused with a pointer to the image path, so a dropped
  `.mp4` explains itself instead of doing nothing.

### 7. Panic safety

`[profile.release] panic = "abort"` becomes `"unwind"`; extraction is wrapped in
`catch_unwind` inside the blocking task, so a third-party parser panic returns
`ExtractError::Crashed` and a toast. A test pins that a deliberately panicking
extractor is contained.

## Non-goals

- OCR, embeddings, retrieval, chunk ranking, vector search.
- Legacy binary Office (`.doc`, `.ppt`) and OpenDocument other than `.ods`.
- Editing or previewing documents inside the app (the reference's split viewer).
- A document library UI beyond the existing project Docs tab.
- Media (video, audio, gif) and any change to the image/vision path.

## Risks

- `pdf-extract` quality varies on unusual PDFs; the `NoTextLayer` path and the
  reader tool are the fallback, and the failure is always visible.
- Content-addressed storage changes where new project docs are written; legacy
  rows keep their old path via the stored-path read, but the two locations
  coexist until those documents are re-added. Called out in the release doc.
- Attach-time extraction makes a 10 MiB PDF a blocking-ish step; it runs in
  `spawn_blocking`, and the chip shows a pending state so the composer stays
  responsive.
- Three docs per message with 40 000 chars each is ~30 000 tokens; the per-turn
  trim keeps that inside a small model's window, and the notice tells the model
  to page with `read_document`.

## Deviations as shipped

Sections above are the plan as written; this is what the code does where the two
differ.

1. **No `pages` field.** The extractor returns `String` (`ExtractResult<String>`);
   nothing counts pages or cells for the card, which shows the extracted
   character count instead.
2. **Rows are written at send time, not at attach time.** `attachment_ingest`
   takes no conversation id: a brand-new chat has none while the composer is
   still open. Both rows are inserted by `commitChatDocs` during the send, after
   the conversation exists, so a chip removed before sending leaves no chat row
   and no project reference behind.
3. **No sidecar rollback.** There is one content-addressed file and no per-chat
   copy to roll back: a failed row insert leaves the file unreferenced, and the
   unreferenced wipe (or Delete everything) removes it later. The composer
   reports which names could not be attached.
4. **Failure codes** are `unsupported`, `no_text_layer`, `empty`, `failed`,
   `crashed`, `bad_payload`, `too_large` — `TooLarge` became a code next to the
   others, and `bad_payload` covers a malformed base64 upload.
5. **Trimming is first-come, not proportional.** Each document takes
   `min(40 000, remaining)` of the 120 000-character turn budget, so with the
   three-document cap the aggregate guard never actually binds; it is there for
   the case where that cap rises.
6. **No pending chip.** The composer awaits ingest behind the existing
   `attaching` flag and the chip appears once extraction returns; there is no
   intermediate "reading…" state.
7. **`parseMessageAttachments` returns the union.** The plan had it keep
   returning images for its callers; instead `parseImageAttachments` and
   `parseDocAttachments` filter the union, and `turnContent` plus `MessageImages`
   were moved onto the image-only parser.
8. **The two sidecar write commands went away.** `knowledge_sidecar_write` and
   `knowledge_sidecar_read` (Rust and their `api.ts` wrappers) are removed, since
   nothing writes the legacy layout any more; `knowledge_sidecar_delete`/`wipe`/
   `wipe_all` stay for the files old installs already have, and their text is
   read through the `document_read` fallback.
9. **Sheet caps are fixed numbers**: 20 sheets, 5 000 rows and 64 columns per
   sheet, each omission marked in the extracted text.
10. **A chip release is guarded by the chips still pending.** `releaseChatDoc(doc,
    remaining)` skips the unreferenced wipe while another chip in the composer
    carries the same hash, so removing one of two copies of a file in a chat that
    has no rows yet cannot delete the shared file. A chip pending in a *different*
    conversation is still invisible to the Rust reference check — the durable
    reference is written when a message is sent.
