# v0.5.0 — Memory as one file, with a migration that cannot lose a note

> Ships the file-backed memory from the Oct 22 proposal, with the judge gate
> **deferred** to 0.6.0 and the human inbox kept as the only write gate.
> The release is defined by its migration: a 0.4.1 user upgrades, opens the app,
> and every note they already have is in `MEMORY.md`, readable, editable, and
> still injectable — or the app tells them exactly why it is not.

---

## 1. Why 0.5.0 and not a patch

v0.4.1 is already released — tag `v0.4.1`, merge `c62c624`, shipped 2026-10-22 —
and 0.4.1 is the version live on `main` today. That makes 0.5.0 the next release,
not 0.4.2: `AGENTS.md` limits patches to code/test fixes for features that already
shipped, and this moves where memory lives and rewires the read/write path.

So the upgrade path this document describes is **released v0.4.1 → 0.5.0**. There
is no in-flight 0.4.2 to rebase onto.

No SQL table is dropped in this release. `memories` is frozen, not deleted.

## 2. What ships

| In 0.5.0 | Out (0.6.0) |
| --- | --- |
| `MEMORY.md` per scope, human-editable | Local judge model (ONNX), shadow then gate |
| One-time, idempotent, lossless migration | Auto-consolidation |
| Deterministic filters: secret, source, dedupe | File watcher |
| Inbox stays the gate (`pending_memories` untouched) | Auto-write band above a confidence threshold |
| `recall` / `update` / `delete` read the file | Semantic retrieval |
| Jump-to-latest anchor and a single activity pill | Provider key rotation (S8) |
| T2 context table, S4b columns, S7 import | Generic permissions, YOLO, recent models, OpenCode |

### Layout

```
%APPDATA%\com.abdul.myagent\            (app_data_dir, next to myagent.db)
  memory\
    MEMORY.md                            global
    projects\<uuid>.md                   one per project, only if it has notes
    legacy\
      memories-<utc>.json                full pre-migration dump, never deleted
      unassigned.json                    project rows with no live project
  myagent.db                             memories frozen at migration time
```

Project files are keyed by UUID, never by project name: renames, collisions and
Windows reserved names (`CON`, `PRN`, `NUL`) all stop being a problem. The path
is resolved in Rust from the project id and never taken from a tool argument.

### Format

```markdown
# MEMORY

## User
- Prefers concise answers and ASCII diagrams <!--m:7f2a9c1e5b6d4a3f8c2e1d0b9a8f7e6d 2026-10-22-->
- Reviews every diff before approving a commit <!--m:91c0d2f4a6b8e0c2d4f6a8b0c2e4f6a8 2026-10-22 k:fact-->

## Preferences
- Direct corrections, no padding <!--m:03de5f7a9b1c3d5e7f9a1b3c5d7e9f1a 2026-10-20-->

## Project
- myagent: Tauri + Rust + React/Tailwind, local-first, BYOK <!--m:5b186a9c2e4f8b0d2a6c4e8f0b2d6a4c 2026-10-18-->

## Decisions
- Sandbox runs only `sandbox_run` in Docker; file ops stay on host <!--m:c2a45e8b0d2f4a6c8e0b2d4f6a8c0e2b 2026-10-19-->
```

| Rule | Value |
| --- | --- |
| Headings | `User`, `Preferences`, `Project`, `Decisions` (fixed, in that order) |
| Line | one bullet, text then one anchored comment at end of line |
| Comment | `<!--m:<32 hex> YYYY-MM-DD[ k:<kind>]-->` |
| `id` | the existing UUID, dashes stripped, so audit rows and undo still correlate |
| `k:` | only on migrated rows, and only when the original `kind` is not implied by the heading |
| Text cap | 2000 chars for every note; the send budget, not the write, keeps the file small |
| Newlines | collapsed to one space on write (original survives in the backup JSON) |
| Escaping | `<!--` → `<\!--`, `-->` → `-\->`; reversed on parse. A note can never forge metadata |
| Unknown text | kept verbatim, outside any heading, and re-rendered after the headings |
| Load cap | 2500 chars per scope (not 8 KB — see §5) |

`src`, `conf` and provenance do **not** live in the file. They live in
`audit_log`, which already exists and already has a page. A score inside a line
becomes a lie the first time a human edits it.

## 3. What a 0.4.1 user actually has

Inventory, from the live schema:

| Source | Detail |
| --- | --- |
| `memories` | `id, scope, project_id, kind, content (1..2000), created_at, updated_at, source_conversation_id` (`lib.rs:95`, migration 23) |
| `pending_memories` | unreviewed queue, may be non-empty on upgrade (`lib.rs:328`) |
| `projects` | `id, name, description, instructions` — **no filesystem path** (`lib.rs:87`) |
| `audit_log` | 500-row cap, references memory ids in `detail` |
| Disk | no `memory/` directory exists yet; `MEMORY.md` cannot collide with anything |

Rows that need a decision, because they exist in real databases:

| Case | Counts as | 0.5.0 behaviour |
| --- | --- | --- |
| `scope='project'` with a live `project_id` | normal | `projects/<uuid>.md`, `## Project` |
| `scope='project'` with `project_id = NULL` | orphan | `legacy/unassigned.json`, banner in Settings |
| `scope='project'` with a deleted project | orphan | same |
| unknown `kind` | fallback | `## Decisions` + `k:<original>`, counted in the report |
| unknown `scope` | fallback | global, counted |
| content > 200 chars | long | kept whole, counted, not truncated |
| content with `\n` | multi-line | flattened, original kept in backup |
| two identical notes | duplicate | both kept; "N duplicates" action in Settings, never merged automatically |
| whitespace-only content | empty | skipped, counted, preserved in backup |
| `source_conversation_id` → deleted chat | label only | id kept; UI already falls back to "from a chat" |

Migration never merges, never truncates, never drops. The only rows that do not
land in `MEMORY.md` are orphans, and they land in a file plus a UI list.

## 4. Migration

### Trigger and order

```
app boot
  └─ getDb()                     tauri-plugin-sql runs migrations 1..27
      └─ memory_migrate          Rust, once, idempotent
          └─ refreshMemories     reads files (or DB fallback)
```

Frontend-triggered, not `setup()`: the SQL plugin's migrations are what create
`memories`, and `setup()` can run before they do. The store already awaits
`getDb()` and `refreshMemories()` before `setReady(true)`, so this adds one
awaited call in an existing chain (`store.tsx:659`).

SQL migration **28** is additive only (27 belongs to the S4b audit columns):

```sql
CREATE TABLE IF NOT EXISTS meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

### Steps

1. Read `meta['memory.migrated']`. Present → return the stored report. Done.
2. `MEMORY.md` already exists → write the marker with `reason: "file-present"`,
   return "already on file memory". **Never import over an existing file.**
   This single rule makes the crash-after-write case and the
   "user restored their own file" case both safe.
3. Read every row, `ORDER BY created_at ASC, id ASC`, including
   `source_conversation_id`.
4. Read live project ids.
5. Write `memory/legacy/memories-<utc>.json` **before** any file write:
   every row verbatim, schema version, counts, app version. `fsync` it. If this
   fails, stop and leave the DB untouched — the user is still on 0.4.1
   behaviour.
6. Build and atomically write each file: `.tmp` → `rename`. No partial file can
   exist.
7. Write `memory/legacy/unassigned.json` if there are orphans.
8. Write `meta['memory.migrated']` = `{ at, files, counts, legacy, version }`.
9. Return the report to the UI.

### Invariants

- **The DB is never modified.** No `UPDATE`, no `DELETE`, no `DROP`. A failed
  migration leaves 0.4.1 data untouched.
- **Backup before file.** Step 5 precedes step 6.
- **File existence is the idempotency key**, not the marker. A lost marker
  cannot duplicate notes.
- **Memory is available even when migration fails.** If there is no file and no
  marker, reads fall back to `memories` and the UI shows a compatibility banner.
  The feature degrades, it does not disappear.
- **Pending stays pending.** `pending_memories` is not touched; the inbox still
  shows the same unreviewed notes after upgrade.

### Failure matrix

| Failure | On-disk state | Next launch | User sees |
| --- | --- | --- | --- |
| disk full in step 5 | DB only | retry | banner: "memory still in compatibility mode" |
| crash after step 6, before 8 | files, no marker | marker written, no import | nothing (already correct) |
| AV holds the target file | DB only | retry | same banner, memory still works |
| marker written, files deleted by user | marker, no file | no import (marker) | empty memory; "Import from backup" action |
| file corrupt | marker + bad file | parse salvage | banner, send still works |
| file read-only | marker + file | writes rejected | toast on save, no silent loss |

### Rollback and the two-version window

Reinstalling 0.4.1 reads the frozen `memories` table: every note as of the
migration is there, anything added on 0.5.0 is not. Documented in the release
note as "downgrade shows memory as of the upgrade".

On re-upgrade, the marker says done, so rows written by 0.4.1 during the
downgrade would be invisible. `memory_import_legacy` covers exactly that: it
diffs `memories` against the file and offers "3 notes from the old store are not
in your memory file — Review". **Offer, never auto-import**, because the user may
have deliberately deleted those lines in 0.5.0.

### The one-time report

Shown once, from the marker, with `Revoke`-style dismiss:

> **Memory moved to a file.** 14 notes imported (11 global, 3 project), 2 project
> notes had no project. Backup: `memory/legacy/memories-2026-10-22T…json`.
> [Open MEMORY.md] [Review 2 unassigned]

## 5. Prompt budget, corrected

The proposal's 8 KB per scope does not fit. `MAX_CHARS = 6000` is the **whole**
system prompt — identity, standing instructions, memory, project block, per-chat
prompt, knowledge and skills (`context.ts:6`, `context.ts:63`). Two 8 KB files
would be ~2.7× the entire budget.

- `MEMORY_BUDGET = 2500` chars per scope, enforced at render.
- Heading overhead counted.
- If the assembled prompt is still over, keep identity and memory and clip
  knowledge/skills first (the current order), then say so.
- Settings shows **"N notes not sent"** whenever the cap drops lines. The silent
  truncation this release is fixing must not survive in a new place.

## 6. Runtime

### Read

On every send: `stat` both files (mtime + len). Unchanged → cached render.
Changed → re-parse. No watcher, no `notify` dependency, no rename/AV races.
A read error uses the last good render and logs once; a send never fails because
of memory.

`buildSystemPrompt` keeps its current block order, projecting the file:

```
## Durable memory            <- global file, metadata stripped
## Project: <name>
### Project memory           <- projects/<id>.md, metadata stripped
```

Project wins on conflict, as today (global renders before project).

### Write

One Rust module, one lock, atomic rename. Scope is a typed argument, never a
path from the model.

```rust
// src/memory/file.rs
pub fn parse(md: &str) -> Doc;           // keeps unknown text verbatim
pub fn render(doc: &Doc) -> String;

// src/memory/store.rs
pub fn append(scope: Scope, e: &Entry) -> Result<()>;
pub fn update(scope: Scope, id: &str, text: &str) -> Result<()>;
pub fn forget(scope: Scope, id: &str) -> Result<bool>;
pub fn replace_raw(scope: Scope, md: &str, expected_mtime: u64) -> Result<()>; // editor
pub fn assign(scope: Scope, id: &str) -> Result<()>;                          // orphan
```

### Tauri commands

```
memory_migrate          -> MigrationReport
memory_read             -> { global: String, project: Option<String>, stats }
memory_write_raw        -> (editor; mtime conflict guard)
memory_forget           -> bool
memory_assign_legacy    -> ()
memory_import_legacy    -> Diff
memory_export           -> { markdown, parsed, pending }
memory_project_delete   -> ()     // called by deleteProject
memory_reset            -> ()     // called by wipeAll
```

### Existing call sites that must move

| Today | 0.5.0 |
| --- | --- |
| `db.listMemories` (`db.ts:722`) | `memory_read` + parse |
| `db.createMemory` (`db.ts:739`) | `memory_write_raw` append |
| `db.updateMemory` (`db.ts:763`) | `memory_write_raw` by id |
| `db.deleteMemory` (`db.ts:775`) | `memory_forget` |
| `db.approvePendingMemory` (`db.ts:791`) | Rust: append file, then delete pending row |
| `db.restorePendingMemory` (`db.ts:805`) | Rust: remove line, then re-insert pending |
| `tools.rs remember` → `pending_memories` | unchanged (inbox stays SQLite) |
| `tools.rs recall_memory` (`tools.rs:1330`) | parse both files, same output shape and ids |
| `tools.rs update/delete_memory` | file rewrite; delete still approval-scoped to the id |
| `deleteProject` (`db.ts:705`) | also `memory_project_delete` |
| `wipeAll` (`db.ts:189`) | also `memory_reset` (deletes `memory/`, including backups) |
| `memory-export.ts` | markdown + parsed + pending |

`remember` still writes to `pending_memories`; approval is what puts a line in
the file. **The file never contains unreviewed text** — that is why the judge is
not needed to make this safe.

### Editor conflict guard

`memory_write_raw` compares the file's mtime+size with what the editor loaded.
Changed → reject with "changed on disk", offer reload or overwrite. Without this,
the Settings editor silently clobbers a hand edit made five seconds earlier.

### Deterministic filters (new, no model)

Applied to `remember` proposals before they enter the inbox:

1. **Secret/PII scan** — `looks_secret()` from `features.md:422`: `sk-`, `ghp_`,
   `AKIA`, long hex/base64, private key headers, `password=`, `token=`,
   `Bearer`. Refuse and tell the user.
2. **Turn trust** — if the turn called `web_fetch`, `web_search`, `sandbox_read`
   or a document reader, the candidate is tagged `untrusted` and can never be
   auto-accepted later. Rust knows this from the tool log; the model cannot
   spoof it.
3. **Dedupe** — normalized equality against the target file; exact duplicate
   refreshes `at` instead of adding a line.

Filters can only **drop**, never approve. The proposal's escalate-only rule is
kept, just pointed at the inbox.

## 8. Tests

**Rust, `file.rs`** — round-trip; unknown paragraph and unknown comment survive;
`##` inside note text; `<!--` escape/unescape; dashless id canonicalization;
duplicate id detection; empty file; file with only a heading.

**Rust, `store.rs`** — atomic write leaves no `.tmp`; two writers serialize;
`replace_raw` rejects a stale mtime; path jail rejects `../` project ids;
forget by id is exact; append preserves file order.

**Rust, `migrate.rs`** — fixture per row case in §3; empty DB; 2000-char row;
newlines; duplicates; unknown kind; orphan project; missing project; second run
is a no-op; file-pre-exists is a no-op; marker lost + file present does not
duplicate; backup JSON equals the table; write failure leaves DB untouched.

**Vitest** — bootstrap calls `memory_migrate` before `refreshMemories`;
migration failure shows the banner and still opens chats; editor conflict path;
`wipeAll` removes `memory/`; export contains markdown and parsed notes.

**Manual QA** — upgrade from a real 0.4.1 DB; edit in Notepad between turns;
delete the file while the app is open; set the file read-only; kill the app
mid-migration; downgrade, add a note, re-upgrade.

## 9. Accepted risks

- **No downgrade support.** Documented; `import_legacy` recovers the common case.
- **`memories` goes stale from 0.5.0 onward.** Frozen by design; a future release
  drops it after one stable cycle.
- **External edits are not audited.** The file is the record; `audit_log`
  records agent decisions only.
- **One file per project, not per workspace folder.** Projects have no path in
  this app; tying memory to the sandbox folder would put it in a writable mount.

## 10. Decided (2026-10-22)

1. **2500 chars per scope**, not 8 KB. Forced by the 6000-char prompt budget.
2. **Four headings**, not six. `Feedback` → `Preferences`, `References` → `Project`.
3. **Orphans go to `legacy/unassigned.json` + a banner**, never silently promoted
   to global.
4. **Backup is memory-only JSON**, not a copy of `myagent.db`. Copying a live
   SQLite file without its WAL is how you get a broken backup.
5. **File lives in Roaming app data**, beside `myagent.db`; OneDrive conflict
   handling is the user's, and atomic rename keeps it recoverable.
6. **Activity pill:** centered while the transcript is empty, inline above the
   composer after that. One mount, never both.
7. **Jump to latest:** bottom-center of the chat area, 16px up, sibling of the
   scroller.
8. **Provider rotation (S8):** 0.6.0, skip the exhausted key and retry it after
   a 10-minute cooldown.
9. **Generic permissions, YOLO, recent models, OpenCode:** parked in
   `docs/later.md`, not 0.5.0.
