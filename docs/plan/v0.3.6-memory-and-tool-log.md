# v0.3.6 — memory editing and a tool log that stays

Three items the owner reported after living on 0.3.5. Research fan-out (three
read-only scouts: tool-log lifecycle, memory tool surface, native dialog
inventory) produced the evidence below before any file changed.

## Summary

1. **The tool-call UI vanished when a reply landed.** `ToolLogView` was mounted
   only while `live` (`MessageList.tsx:411`, `:386`) and read one global store
   array (`store.tsx:404`). The stream `finally` set `streamingId` to null
   (`:1390`), the mount condition went false, and the component unmounted — even
   though `tool_log` had been persisted (`:1144`, `:1158` → `db.ts:504`).
   Artifacts survived the same moment because they render from the message
   (`MessageList.tsx:389`, `:433`); the tool log had no such path.
2. **No `update_memory` / `delete_memory`.** The model had `remember` (write) and
   `recall_memory` (read); the table has a UUID id (`lib.rs:77-98`) and
   `recall_memory` never printed it (`tools.rs:890-901`).
3. **Two native `window.confirm` calls** — `MemoryEditor.tsx:139` and
   `ProjectDialog.tsx:87`. No `alert`/`prompt` anywhere, no Tauri dialog plugin
   (`Cargo.toml:24-26`). `DESIGN.md:250,260,300` and
   `docs/references/design-system.md:56-60` require the themed confirm.

## Decisions (owner-answered)

| Question | Answer |
|---|---|
| Release | v0.3.6 (v0.4.0 keeps the sandbox scope) |
| Tool log after a turn | visible always and stored (survives reload) |
| Addressing a memory | `recall_memory` prints ids; update/delete require an id |
| Approval | `delete_memory` = ask, `update_memory` = allow |
| Delete recovery | hard delete + audit row |

## Architecture

### 1. Tool log on the message

- `store.tsx` — `toolLog` state and its ref-sync effect are deleted. A local
  `applyToolLog(entries)` inside `streamTurn` writes `toolLogRef.current` and
  patches the assistant message with `toolLogPatch(entries)`; `tool_start` and
  `tool_result` both go through it.
- `streamTurn` clears the message's `tool_log` at turn start, which also covers
  regenerate (`keepSeed`).
- `finalize` uses `settleToolLog` (running → `err` / `Interrupted`), persists the
  JSON as before and patches the in-memory message when a status actually changed.
- `selectConversation` and `branchFrom` lose their restore steps: the rows they
  already load carry `tool_log`.
- `MessageList.tsx` — `ToolLogView` is exported, takes `entries`,
  `collapseToolCalls` and `resetKey`, and returns null on an empty list.
  `AssistantMessage` memoises `parseToolLog(message.tool_log)` and renders it
  whenever the list is non-empty, live turn or reopened chat.

### 2. Memory tools

- `tools.rs` — two specs; `recall_memory` selects `id` and prints `[id]`;
  `update_memory` / `delete_memory` arms validate a UUID id, apply the same
  visibility predicate as recall, and audit. SQL lives in `find_memory_content`,
  `update_memory_row`, `delete_memory_row` so the same statements run in tests.
- `permissions.rs` — `update_memory` `Allow`, `delete_memory` `Ask` in
  `default_rules`.
- `llm.rs` — `approval_resources` returns the row id for both tools;
  `memory_approval_text` resolves that id to text for the approval card, and
  `cwd` reads `saved memory` for these two tools.
- `src/lib/tools.ts` — both names join `KNOWN_TOOLS` for the system-prompt
  sentence.
- `MemoryList`/icons: `update_memory` uses the pencil, `delete_memory` the bin.

### 3. Dialog swap

Both call sites mirror the existing eleven: `await confirmDialog({ title, body,
ok, danger: true })`, then return on cancel. `MemoryEditor` re-checks
`busyRef.current` after the await because the dialog is async where `confirm`
was not.

## Non-goals

- E2 secret refusal on write (still Missing in `features.md`).
- Thread roll-up into project memory (E6's other half).
- Soft delete, undo, or a trash view for memories.
- Ids inside the injected memory block; the model recalls to get one.
- Fixing `cwd`/copy on the approval card for every tool.

## Tests

- `MessageList.test.tsx` — `ToolLogView`: stored log renders with counts and
  previews, empty renders nothing, folded start hides the entries.
- `store.test.ts` — `toolLogPatch` and `settleToolLog`.
- `tools.rs` — `memory_writes_stay_inside_the_visible_scope` (real SQL against an
  in-memory database: cross-project update and delete are refused, no-op update,
  exact-one delete), `memory_ids_must_be_uuids_and_previews_stay_short`.
- `llm.rs` — `memory_edit_tools_are_listed_and_approve_per_row`.
- `permissions.rs` — default rules for the two new tools.

## Risks

- Prompt injection asking for a delete: mitigated by `Ask` on delete, ids only,
  no wildcard argument, and the untrusted-content rule in the system prompt.
- The approval card's "Always allow" writes a per-id rule; a nonexistent id can
  never be targeted again, so the rule is inert rather than dangerous.
- Two writers to `myagent.db` (plugin-sql and the Rust pool) are unchanged; a
  busy database surfaces as a tool error.

## Deviations as shipped

1. **The global tool log array was removed, not kept.** The plan started as
   "mirror onto the message and read whichever is live"; the mirror made the
   array redundant, so `toolLog` left the store context. Fewer states, one
   renderer.
2. **`settleToolLog` and `toolLogPatch` were extracted** from duplication in
   `finalize`, `selectConversation` and `branchFrom` — the latter two then lost
   their restore blocks entirely.
3. **The approval card resolves the memory text.** The plan expected the id in the
   card; showing an opaque UUID before a destructive action read badly, so
   `memory_approval_text` looks the row up (falling back to the plain summary).
4. **`cwd` shows `saved memory`** for these two tools, because `in C:\Users\…`
   above a memory deletion is a lie.
5. **Update/delete validation is shared** (`memory_id_arg`), and the kind list
   became `MEMORY_KINDS`, used by `remember` too.
6. **`(None, None)` update returns 0 rows** in the SQL helper and is rejected in
   the caller, so the helper stays total and tested.
7. **The tool-log fix ships in the same release as the memory tools.** The owner
   asked for all three together; the release doc records all three.
8. **D1's done criterion is satisfied again.** `docs/features.md` D1 "both results
   visible" was true only mid-stream before this release; the status note now
   records the fix.

## Review follow-ups (OCR, commit `ba53ee6`)

OCR was healthy for this cycle (7 of 12 files reviewed, 5 lost to a provider
`400`). Two findings landed on the diff; both were real and are fixed in the
commit that follows.

1. **`continueTurn` lost the first segment's tool calls.** `streamTurn` cleared
   `tool_log` for every call, including the `keepSeed` path used when continuing a
   `length`/`interrupted` reply: the earlier calls vanished from the UI and
   `finalize` then persisted a JSON built only from the new segment. The ref is
   now seeded from the message being continued (`db.parseToolLog(seed?.tool_log)`)
   and the clear happens only when the turn is not a continuation.
2. **The delete dialog did not name its target, and rows stayed live behind it.**
   `confirmDialog` is a singleton that resolves a pending request with `false`, so
   a second request replaces the first, and every row asked the identical "Delete
   this memory?" question. The body now quotes the memory, `MemoryEditor` tracks
   `confirmingId`, and Edit/Delete are disabled while a confirmation is open.
3. **First fix attempt tripped the complexity gate.** `fallow audit --base main`
   found two new CRAP findings in `MemoryEditor.tsx` (the row's render closure at
   6 and `remove` at 5), because `.fallow/health-baseline.json` has no entry for
   that file and the added `||` operators counted. The lock flag is now computed
   once as `rowLocked`, and `remove` uses two early returns plus `runLocked`'s own
   guard, which also removed the redundant post-await busy check. Audit exits 0.
