# Release v0.3.5 — documents in every chat (feature)

Feature release. A chat can now take real files — PDF, Word, spreadsheets,
HTML, markdown, code — with the text extracted inside the app, added to the
message you send, and readable afterwards through a new `read_document` tool.
Attaching no longer requires a project. Migration 21 adds the table that ties a
document to a chat; the extracted text lives in one content-addressed store
shared with project knowledge. `v0.4.0` stays reserved for the sandbox release.

## Scope

| # | Area | Tracked as |
|---|---|---|
| 1 | Format extraction in Rust, panic-guarded | `F3` |
| 2 | One document store for chats and projects, reference-counted | `F3`, `B11` |
| 3 | Composer attachments without a project, chips and caps | `F3` |
| 4 | Injection into the user turn plus the `read_document` tool | `F3`, `D4`, `D13` |
| 5 | Cleanup on every delete path | `B11` |

## What changed

### One store, addressed by content

- Extracted text is written to `<app_data>/documents/<sha256>.txt`, and the row
  keeps the hash, name, mime, byte size and extracted character count. The same
  bytes attached in ten chats are stored once.
- A chat's documents are `chat_docs` rows (migration 21, `UNIQUE(conversation_id,
  sha256)`, `ON DELETE CASCADE`); a project's are the existing `knowledge_docs`
  rows. Sending inside a project writes the chat row *and* a project row that
  points at the same file, so the project reaches it from any chat there. Both
  rows are written when the message is sent, so a chip the user removes before
  sending leaves nothing behind in the project.
- Project documents written before 0.3.5 still live under
  `knowledge/<project>/<sha>.txt`. `document_read` falls back to that path, so no
  file has to be migrated. The two commands that wrote the legacy layout
  (`knowledge_sidecar_write`, `knowledge_sidecar_read`) are gone; the delete and
  wipe commands stay for those old files.

### Extraction covers the formats people actually attach

| Kind | How it is read | Notes |
|---|---|---|
| Text, markdown, code | UTF-8 (BOM honoured) | NUL bytes refuse the file |
| HTML | `htmd` to markdown text | script and style dropped |
| PDF | `pdf-extract` | a scan with no text layer says so |
| DOCX | `docx-rs` | paragraphs and tables |
| XLSX / XLS / ODS | `calamine` | 20 sheets, 5 000 rows, 64 columns, with omission markers; dates, times and durations render as such |

- Sheets are read as a stream, so a workbook whose bounding box spans a million
  rows cannot exhaust memory before the caps apply.

- Classification is by mime first, then by extension, so a file with an empty
  or generic type still lands correctly.
- Media is refused with a pointer to the image button; legacy binaries
  (`doc`, `ppt`, `pptx`, `odt`, `epub`, `msg`, `rtf`, `pages`, `numbers`, `key`)
  are refused as unsupported. So is a page that nests tags hundreds deep.
- Every outcome is a typed failure — `unsupported`, `no_text_layer`, `empty`,
  `failed`, `crashed`, `bad_payload`, `too_large` — surfaced in the composer as
  a short message rather than a silence.
- Extraction runs on a blocking thread behind `catch_unwind`, and the release
  profile switched to `panic = "unwind"` so a parser panic on a damaged file
  becomes an error the app can show instead of a closed window.
- Text is capped at 2 MB; the cap reserves room for its own truncation marker,
  so a capped document never claims more than it carries.

### Attach without a project, capped and visible

- The project-only guard is gone: any chat takes files. Images keep their own
  path and the image button.
- Up to three documents per message and 10 MB per file, checked before the bytes
  are read. Chips show the name, size and extracted character count; removing a
  chip frees the file only when nothing else points at it, including a second
  chip still in the composer.
- A file already attached to the chat is detected by hash and reused instead of
  stored twice.
- The reference is saved on the message, so reopening the chat shows the
  document card again. Branching a chat copies its document rows.

### The turn carries the text; the tool fetches more

- The last user turn is sent with each document's text inside a
  `<source name="…" type="…">` block, in the user message rather than the system
  prompt: 40 000 characters per file and 120 000 per turn, with a marker naming
  how much was left out.
- Injection is payload-only — the message body on disk keeps the original text —
  so regenerate and edit-resubmit re-inject the same way, and no document text is
  duplicated into the transcript.
- Document text is treated as data, not instruction: the wrapper tags are
  stripped from the body, the name and mime are flattened into the attributes,
  and the system prompt says attached-document content is untrusted.
- `read_document` is offered only when the chat holds documents. It lists them,
  resolves one by exact hash, file name, substring or hash prefix, and returns a
  capped slice, optionally filtered by a pattern; spills behave like other tool
  output. It is allowed by default, like the other read-only tools.

### Deleting frees the text

- `documents_wipe_unreferenced(shas)` looks in both `chat_docs` and
  `knowledge_docs` and removes only files nothing points at. Deleting a chat,
  clearing a chat, removing a project document, deleting a project and Delete
  everything all go through it (Delete everything wipes the whole directory).

## Upgrade path (from 0.3.4)

- Migration 21 adds `chat_docs` and its index; no existing row changes shape.
- Project documents written before this release stay readable through the
  legacy path; their rows are untouched.
- A 0.3.5 database opened by a 0.3.4 build leaves the new table unused. A
  message that carries a document reference loses its whole attachment list
  there (0.3.4 only knows `{dataUrl}`), which is why downgrade is untested, as
  before.

## Not in this release

- OCR and scanned PDFs; embedded media, charts and images inside documents.
- Legacy `.doc`/`.ppt` binaries and non-Excel spreadsheets (`.numbers`).
- Attaching from the project Docs tab; that tab still lists and removes.
- Everything planned for `v0.4.0` (sandbox, decision models, voice, subagents,
  research) — see `docs/releases/v0.4.0.md`.

## Supply chain

The SafeDep scan on the PR flags `zip 8.6.0`, pulled in transitively by
`calamine` and `docx-rs`. The advisory (RUSTSEC-2026-0367) is fixed only in
`zip 9.0.0` and both crates still pin `zip = 8`, so there is no upgrade to make.
It covers the extraction APIs — the ones that write entries to disk with
attacker-controlled paths, permissions or symlinks — and this app calls none of
them: its own code has no zip references, and the two crates only open
`ZipArchive::new` and read entries in memory. Tracked in `docs/later.md`.
