# Release v0.5.1 — Responses API fallback (patch)

Status: unreleased. Follows v0.5.0. No migration.

AgentRouter's current GPT catalogue (`gpt-5.6-sol`, `gpt-6-astra`,
`gpt-6.1-sol`) rejects `/v1/chat/completions`:

```
400 Bad Request: … does not support /v1/chat/completions, use /v1/responses
```

0.5.1 detects that response once per model and retries against `/v1/responses`.
Chat, tools, titles and summaries keep working without a new setting.

## What changes

- **Automatic fallback.** A 400 containing the Chat Completions marker marks the
  `base_url|model` pair for the rest of the process. Later requests go straight to
  `/responses`. A restart re-probes once.
- **Responses request body.** Messages become `input[]`; tools are flattened; the
  request is stateless (`store:false`); `temperature` is omitted; reasoning effort
  is sent as `reasoning.effort`, and encrypted reasoning is requested only when an
  effort is sent.
- **Responses streaming.** Text, refusals, reasoning summaries, function-call
  arguments, usage and finish reasons map onto the existing events.
- **Tool loop.** Function calls carry `call_id`; results go back as
  `function_call_output`; raw reasoning/message/function-call items are replayed
  from the completed response. A call or assistant message omitted from a partial
  completed output is filled from the Chat-shaped history.
- **Titles and summaries.** `complete_text`, `summarize` and `suggest_title` go
  straight to Responses once a model is marked, and read
  `output[].content[].output_text`. Failed or empty non-stream bodies are errors,
  not empty titles.
- **No UI change.** The provider picker, model picker, composer and approval flow
  are unchanged.

## What does not change

- No SQL migration and no data move.
- Memory stays file-backed as shipped in 0.5.0.
- MCP transport and authorization are untouched; MCP OAuth is 0.6.0.
- No new provider setting, no stored response id, no provider-side retention.

## Upgrade path

Install 0.5.1 over 0.5.0. The first message to an AgentRouter GPT model may make
one extra request (the Chat Completions probe); subsequent messages go directly
to Responses. Existing chats, keys and memory are untouched.

## Failure behaviour

- If Responses also rejects the request, its error is shown; there is no retry
  loop.
- A 401/403 is still a key or access error, not a mode switch.
- 429/5xx keep the existing backoff.
- Cancelling mid-stream does not start a second request.
- A marker that arrives after visible text or a tool start is surfaced, not
  retried, so the user never sees two answers.
- Oversized text, reasoning, SSE events or tool arguments stop with a typed
  upstream error; a partial tool call is never executed.
- A response containing no text and no tool call reports
  `empty response from provider`; a non-stream body with `status:"failed"` or a
  top-level `error` reports the provider message.
