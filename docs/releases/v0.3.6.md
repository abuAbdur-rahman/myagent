# Release v0.3.6 — memory editing and a tool log that stays (fix + feature)

Follows v0.3.5. Three user-reported items: the tool-call list vanished the moment
a reply landed, the model could write memories but never fix or drop one, and the
two destructive confirmations still used the bare Windows prompt. No migration,
no schema change. `v0.4.0` stays reserved for the sandbox release.

## Scope

| # | Area | Tracked as |
|---|---|---|
| 1 | Tool-call log rendered from the message instead of live store state | `D1`, `D2` |
| 2 | `update_memory` + `delete_memory`, ids printed by `recall_memory` | `E1`, `E6`, `D4` |
| 3 | `window.confirm` replaced by the in-app confirm dialog | `D5`, `B11` |

## What changed

### The tool log is stored on the message, not on the stream

- The log used to live in one global store array and was mounted only while its
  message was streaming. When the stream ended the mount condition went false and
  the list disappeared, even though `tool_log` had already been written to the
  message row. Nothing ever read that column back.
- The log now mirrors onto the assistant message on every `tool_start` and
  `tool_result`, through the same path artifacts already used, and
  `AssistantMessage` renders it from `message.tool_log`. The global array is gone
  from the store, so there is one source of truth for a live turn and a reopened
  chat alike.
- A turn that is stopped or fails settles its running entries to `Interrupted`
  in the same helper that builds the persisted JSON, so the in-memory message and
  the row agree (`settleToolLog`, `toolLogPatch`).
- Continuing a stopped or truncated reply (`continueTurn`) seeds the log from the
  message it is continuing instead of clearing it. Without that, the first
  segment's calls were wiped from the UI and then overwritten in the row by the
  second segment's JSON, losing the earlier list for good.
- `Collapse tool calls` still folds the list when a new turn starts: each new
  assistant message mounts the view folded (or not) per the setting, and a list
  the user expanded stays expanded for that turn.

### Memories can be changed and deleted by the assistant

- `recall_memory` now prints `- [id] (kind, scope) content`. The id is the row's
  UUID, so the model has a stable handle and the user can see which note is which.
- `update_memory(id, content?, kind?)` changes wording, kind, or both; `scope` is
  deliberately not movable, and passing neither field is an error rather than a
  silent no-op. `delete_memory(id)` removes exactly that row.
- Both statements carry the same visibility predicate as `recall_memory`:
  `scope = 'global' OR project_id IS ? OR project_id = ?`. A row in another
  project updates zero rows, and the tool reports "no memory with that id is
  visible in this chat" instead of reaching it.
- The id must parse as a UUID, so a stray string cannot address anything, and it
  is canonicalised to the hyphenated form before it reaches SQL — a simple or
  braced spelling of the same row resolves to that row.
- Defaults in the permission engine: `update_memory` is allowed like `remember`;
  `delete_memory` asks. The approval card resolves the id to the memory text
  before showing it (`Delete memory: …` / `Update memory from: … to: …`) and
  shows `in saved memory` instead of a home directory.
- The approval resource for both tools is the canonical row id, not the tool name,
  so "Always allow" pins one row and can never blanket-allow deletion; an id that
  is not a UUID falls back to the bare tool name and stores no wildcard.
- `delete_memory` writes an `audit_log` row with the text it removed;
  `update_memory` writes the new text. Deletion is hard — no soft-delete column.

### Destructive confirmations use the app's dialog

- `MemoryEditor` and `ProjectDialog` called `window.confirm`, which renders the
  unthemed WebView2 prompt titled `tauri://localhost says`, cannot be styled, and
  blocks the renderer. Both now `await confirmDialog(...)` with a specific title,
  the consequence, a verb button (`Delete`, `Delete project`) and `danger: true`,
  matching the eleven existing call sites.
- The memory dialog names its target: the body quotes the memory about to go, and
  every row's Edit and Delete buttons are disabled while a confirmation is open.
  `confirmDialog` is a module-level singleton, so a second request replaces the
  first, and identical wording for every row made it possible to confirm one and
  delete another.
- The dialog is asynchronous where `window.confirm` was not, so the delete runs
  through the editor's existing `runLocked` guard and a second confirmation is
  refused while one is open.

## Tests

- `src/components/MessageList.test.tsx` — `ToolLogView` renders a stored two-entry
  log with its count, failure count and previews; renders nothing when the turn
  ran no tools; starts folded when the setting is on. This is the regression guard
  for the disappearing list, since the view no longer depends on streaming state.
- `src/lib/store.test.ts` — `toolLogPatch` stores JSON for a non-empty log and
  `null` for an empty one; `settleToolLog` marks a running entry `Interrupted`,
  leaves finished entries alone, and is referentially stable when nothing runs.
- `src-tauri/src/tools.rs` — `memory_writes_stay_inside_the_visible_scope` drives
  the real SQL through an in-memory database: a global row updates, another
  project's row updates zero rows and stays, `find_memory_content` hides it,
  delete of it removes nothing, `(None, None)` is a no-op, and deleting the global
  row removes exactly that one. `memory_ids_must_be_uuids_and_previews_stay_short`
  covers id parsing and the 160-char preview.
- `src-tauri/src/llm.rs` — the four memory tools are listed, and
  `approval_resources` pins `delete_memory` and `update_memory` to the row id.
- `src-tauri/src/permissions.rs` — `update_memory` is `Allow`, `delete_memory` is
  `Ask` under the default rules.

## Upgrade path (from 0.3.5)

- No migration and no schema change. A 0.3.6 database is byte-compatible with
  0.3.5; `tool_log` and `memories` keep their shape.
- Two new tool names reach the model. A provider that rejects the `tools`
  parameter degrades to a plain completion as before.
- A 0.3.5 build reading a 0.3.6 database ignores the new tools; nothing else
  changed, so downgrade is safe for the first time since 0.3.2.

## Not in this release

- E2 secret refusal before a memory write (`docs/features.md`). `update_memory`
  reuses the same validation as `remember` — kind, scope and the 2000-char cap —
  and will pick E2 up when it lands rather than adding a second unchecked writer.
- Thread roll-up into project memory, the rest of E6.
- Soft-delete or undo for a deleted memory; hard delete plus an audit row only.
- Ids in the injected memory block: the model recalls to get one.
- Everything planned for `v0.4.0` — sandbox, decision models, voice, subagents,
  research (`docs/releases/v0.4.0.md`).
